Why we build offline-first, not offline-tolerant

Most apps treat "no connection" as an error state — something to catch, show a friendly message for, and recover from once the network comes back. That works fine if your users are occasionally offline. It doesn't work if they're occasionally online.

That's the actual condition for most of the people using our products. A shopkeeper in Kariakoo doesn't have a bad connection — she has an intermittent one, and the app has to be useful in both states without her thinking about which one she's in. So we don't treat offline as an exception path. It's the default assumption the architecture is built around, and "online" is the bonus case.

What that looks like in Daftari

Daftari's transaction ledger writes to a local queue first, always — whether or not the device has a connection. If navigator.onLine is false, the transaction goes into a client-side queue with a generated UUID and an is_synced: false flag. There's no "try to save, catch the error, queue it as a fallback" logic, because that ordering assumes online is the normal path and offline is the exception. We inverted it: every write goes to the queue, and syncing to the server is a background concern layered on top.

On the backend, the database layer supports two modes behind one interface — PostgreSQL via Supabase in production, SQLite with write-ahead logging as a local fallback. The DB_MODE environment variable switches between them, which matters for a reason that has nothing to do with rural connectivity: it means we can develop and demo the entire product with zero cloud dependency, which turned out to be just as valuable when a conference wifi network failed during a live demo as it is for a merchant with patchy 3G.

What that looks like in NENA

NENA's constraint is sharper, because the offline requirement isn't just about UX — it's a privacy requirement too. Gesture recognition has to run entirely on-device: the few-shot classifier processes camera frames locally and never uploads video, which means the sign-to-speech pipeline has to work whether or not the phone has signal at that exact moment. That's also why the target latency budget (1.5 seconds, p90, on hardware roughly equivalent to a Snapdragon 665) is a hard on-device number, not a round-trip-to-a-server number. If the model lived in the cloud, the latency budget would be dominated by network variance we can't control — so it doesn't live in the cloud.

The one place NENA does need a live connection — Nena Call, the VoIP relay — is designed to degrade honestly rather than pretend the network isn't there: it targets stability on a real 3G connection (≥1 Mbps) and keeps bandwidth to around 200 kbps by transmitting recognized text tokens instead of video or raw audio where possible, rather than assuming a fast, stable pipe exists.

The trade-off we're not pretending away

Offline-first isn't free. It means more state to reconcile, more edge cases around conflicting writes, and — for the compliance advisor in Daftari — a harder question about what to do when a user asks a question offline and there's no cached answer. We don't have a universally satisfying answer to that last one yet; right now it just fails honestly and tells the user to try again once connected, rather than guessing. That's a real gap, not a solved problem, and it's on the list.

The reason we keep defaulting to this pattern anyway is simple: a feature that only works when the network cooperates isn't a feature for the people we're building for — it's a demo.
